*Estimating exec intensity********************************************
The algo will need to be changed once intensity and branch probability
annotations are added.
Problem: C functions are polymorphic, so they don't correspond to a
single instance. That could be resolved via optional type pattern
guards on annots, e.g. @intensity k if List a -> ().

Simple to start with: assume all branches have equal probability;
exec starts at the main entry point.
Algo: divide BBs into SCCs; for each SCC, compute the intensity effect 
of entry at each enterable BB in it. Effect: intensity for each BB in
the SCC + entry intensity for each out-edge to a lower SCC.
Equation: for each BB b, intensity[b] = sum p[i][b] * intensity[i] for 
each in-edge i.
ifte probability 0.5 implies while loop iteration count 1... too low.
A recursive function could get an infinite intensity, cf
f() := {
 if cond1
 then if cond2
      then return ()
      else ()
      end
 else ()
 end;
 f()
}
With 50% branch probability, that gives a 75% probability of
recursion, i.e. f is expected to call f 4 times.
That's fine... the real problem is
f() := if cond then {f();f();f()} else () end
Quick and dirty solution: compute intensity numerically, iterate over
each BB at most N times.
With inlining and TCO, there isn't a clear separation between C
functions in Core.

Consider HOFs: should I record expected number of calls for each
parameter, or just ignore params other than $ret?

With mutually recursive functions, an SCC could have back-edges to
multiple members. If you treat back-edges as out-edges and cap
intensity to prevent divergence... each entrypoint has a different
out-edge vector.
Really simple scheme: if an SCC is nontrivial, treat back-edges as
exits and just scale intensity by 4.
Note internal edges are not back-edges: SCCs form a tree with
out-edges, exits and back-edges as leaves.
Ex: A -> B or C; B,C -> D; D -> out or A. B and C will have half the
intensity of A.

Degenerate case: SCCs with no leaf nodes. Those can be replaced with
revertValue(). Reverting code paths can be assumed to have intensity
0, leading to an increase in the intensity of their siblings.
Problem: function calls. A C function either diverges, exits or
returns, so you can make a leaf vec for it as well.

Dep graph algo:
source : Map Var LHS --param
--LHS can be used as op key
borrowers = {} : Map Var (Set LHS)
consumer = {} : Map Var LHS
depends = {} : Map LHS (Set LHS)
for (lhs,(op,args)) in ops:
 for v in args: lhs depends on source of v
 (_,svars) = args
 effs <- look up consume/borrow effect per svar arg in args for op 
 if |svars| /= |effs| the op is malformed
 for svar in svars:
  if borrowed: borrowers[svar] += lhs --default borrowers[svar] = {}
  else consumer[svar] = lhs --fails if two conflicting consumers
dependencies from borrowing have already been recorded
for (svar,lhs) in consumer:
 lhs depends on all lhses in borrowers[svar]
a depends on b => depends[a] += b
a depends on all bset => depends[a] union= bset
